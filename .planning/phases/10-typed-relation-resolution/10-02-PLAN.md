<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Ref._target_cls → self.read(target_cls, ids) | An attacker-influenced Ref.id (from a server-returned m2o tuple) reaches the dispatch branch and is forwarded to the existing OdooClient.read(type[T], ids) path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-03 | Tampering | Attacker-influenced `Ref.id` passed to `read(target_cls, ids)` | accept | `Ref.id` is an int from a previously-authenticated Odoo JSON-RPC response. The existing `read(type[T], ids)` path already accepts caller-supplied integer ids and sends them to Odoo over an authenticated session. No new trust boundary is introduced — the Ref dispatcher is an in-process routing layer, not an external surface. Odoo-side ACLs remain the enforcement boundary. |
| T-10-04 | Elevation of Privilege | Untyped-ref guard bypass — `_target_cls=None` slipping past the fail-fast check | mitigate | Guard is the first thing in the Ref branch: `bad = [r for r in refs if r._target_cls is None]`; raises `OdooValidationError` before any `await`. `_target_cls` defaults to `None` on `Ref` construction; only `_pydantic_transform.py` populates it with a real type — wire data cannot forge a non-None value. |
| T-10-05 | Denial of Service | Degenerate `refs` list with many distinct target classes triggers many RPCs | accept | Caller-controlled input, within an authenticated session; no different from calling `read()` in a loop. Production callers hold typed Refs from wire transforms — the distinct-model cardinality is bounded by the schema. No rate-limit or size guard needed at SDK level for v1.2. |
| T-10-SC | Tampering | npm/pip/cargo installs | N/A | No new packages installed in this plan. |
</threat_model>
